# AVSS Process Document — Project Guide

Interactive process-documentation app for Instrata's AV Shared Services (AVSS) team.
It renders the **Pre-Sales** and **Post-Sales** AV workflows as clickable flow charts
with slide-out step detail panels, plus a **Manager edit mode** for authoring step
content. It ships as a **single standalone HTML file** today and is intended to be
folded into the larger **Instrata project tools app** as a feature later.

---

## 1. The one thing you must know: source vs. build artifact

There are **two** files named `Process Doc.html`. Do not confuse them.

| Path | Role | Edit it? |
|---|---|---|
| `design-package/process-doc-2026/project/Process Doc.html` | **SOURCE** — HTML structure, all CSS, all JS (routing, rendering, edit mode) | ✅ Yes — edit here |
| `Process Doc.html` (repo root) | **BUILD ARTIFACT** — generated, self-contained, ~187 KB | ❌ No — regenerated by build |
| `design-package/process-doc-2026/project/steps.js` | **SOURCE** — all step content/data | ✅ Yes — edit here |
| `build.ps1` (repo root) | Build script that produces the root artifact | rarely |

**Workflow for any change:**
1. Edit the SOURCE `Process Doc.html` and/or `steps.js` in `design-package/process-doc-2026/project/`.
2. Run the build: `& "C:\Users\Seth.Powell\CLAUDE CODE\AVSS Onboarding Site\build.ps1"`
   (PowerShell; Python is **not** installed on this machine — don't write Python build scripts).
3. The root `Process Doc.html` is the deliverable. Verify it (see §10).

**What `build.ps1` does:** inlines `assets/colors_and_type.css` and `steps.js` into the
HTML, swaps the local Gantari `@font-face` for the Google Fonts CDN, base64-encodes the
3 referenced images (`logo-wordmark-white.png`, `logo-logomark.png`, `favicon.svg`) into
data URIs, and asserts there are zero leftover `assets/` or `steps.js` references. It
fails loudly if the source structure it expects has changed.

## 3. Data model — `steps.js`

`steps.js` defines a single global: `window.AVSS_STEPS` — a flat array of step objects.
The renderer filters/groups this array; there is no nested tree.

A `_preStep(id, branch, phase, phaseLabel, kind, num, title, ownerKey)` factory builds
pre-sales steps compactly (all pre-sales copy is placeholder — see §6). Post-sales steps
are written as full object literals because they carry real authored content.

**Step shape:**

| Field | Values / meaning |
|---|---|
| `id` | unique int. Pre-sales: 100–250 (sparse). Post-sales: 12–37. |
| `section` | `'pre'` or `'post'` |
| `branch` | pre: `'triage'` \| `'design'` \| `'design-build'` \| `'bid'` \| `'public-bid'` \| `'budget'`. post: always `'main'` |
| `phase` | int (1-based) |
| `phaseLabel` | e.g. `'Intake & Qualification'`, `'Project Setup'` |
| `kind` | `'milestone'` or `'deliverable'` (deliverables get orange rail + "DELIVERABLE" pill) |
| `num` | display label: milestones `M<phase>.<n>` (e.g. `M2.1`), deliverables `D<n>` (e.g. `D1`) |
| `title`, `owner` | strings |
| `ownerKey` | `'sales'` (orange) \| `'avss'` (navy) \| `'ops'` (blue) — drives the owner dot color |
| `actionItem`, `summary` | strings (placeholder `'TBD'` for new steps) |
| `videoUrl` | always `''` — video is a placeholder UI element; no real videos wired yet |
| `details` | array of `{ label?, body }` |
| `notes` | array of strings |

`_OWNER_NAMES` maps ownerKey → default display name for pre-sales. Post-sales uses
custom owner labels (e.g. `'AV PM / Field PM'`).

## 4. Pre-sales structure (Phase 1 triage + 5 branches)

Universal **Phase 1 triage** (`branch: 'triage'`) runs on every project. After triage,
a project falls into exactly **one of five mutually-exclusive branches**. Phase 1 is
rendered at the top of every branch flow (shared data, visually repeated).

| Branch | slug | ID range | Steps |
|---|---|---|---|
| (triage) | `triage` | 100–106 | 7 |
| Design | `design` | 110–121 | 12 |
| Design-Build | `design-build` | 130–152 | 23 |
| Bid | `bid` | 160–188 | 29 |
| Public Bid | `public-bid` | 200–228 | 29 |
| Budget | `budget` | 240–250 | 11 |

Total pre-sales: **111 steps**. All have placeholder `actionItem`/`summary` = `'TBD'`,
empty `details`/`notes` — by design. Real content gets authored later via Manager mode.

`BRANCHES` (in the inline `<script>` of `Process Doc.html`) holds slug → name +
description + drives the overview's branch cards. Terminal bridges differ by branch:
Design and Budget show a blue "END / rolls over" bridge; Design-Build / Bid / Public Bid
show the orange "Contract awarded — kicks off post-sales" bridge.

## 6. Routing (hash-based SPA, in the inline `<script>`)

`route()` parses `window.location.hash` top-down:

| Hash | View |
|---|---|
| `#/` | Landing (Pre-Sales / Post-Sales choice cards) |
| `#/pre` | Pre-sales overview: Phase 1 chart + 5 branch cards |
| `#/pre/step/<id>` | Overview + triage step detail panel |
| `#/pre/<branch>` | Branch flow (Phase 1 + branch phases + terminal bridge) |
| `#/pre/<branch>/step/<id>` | Branch flow + step detail panel |
| `#/post` | Post-sales flow |
| `#/post/step/<id>` | Post-sales flow + step detail panel |
| `#/step/<id>` | **Legacy** — auto-redirects to the step's modern URL |

Unknown branch slugs redirect to `#/pre`. Invalid step IDs redirect to the parent flow.

## 7. Rendering pipeline

All flow charts funnel through shared helpers:

- `nodeHtml(step, activeId, hrefBase)` — one clickable node. Adds `.deliverable` class +
  `<span class="node-kind-pill">Deliverable</span>` when `kind === 'deliverable'`.
  `hrefBase` makes links context-aware (`#/pre`, `#/pre/<branch>`, or `#/post`).
- `groupByPhase(steps)` → `[{ phase, phaseLabel, steps }]`, preserving array order.
- `renderPhaseGroup(label, steps, activeId, hrefBase)` — a `.subgroup` header
  ("Phase N · Label") + a `.col` of nodes joined by `arrow()` connectors.
- View renderers: `renderLanding`, `renderPreOverview`, `renderBranchFlow`,
  `renderPostFlow` — all compose `renderPhaseGroup`.
- `renderInlineDetail(id, which)` — the right-hand slide-out panel. `which` is
  `'pre'` | `'post'` | a branch slug; it derives the back-link target, the prev/next
  sequence (triage → branch order in branch context; section order in post),
  breadcrumb, and video pill label from it.
- `setCrumbs(state)` — top-bar breadcrumb (`Process Document / … / Step`).

Branch flow / post-sales chart collapses to ~1/3 width when a detail panel is open
(`.flow-split.has-detail`); the deliverable "DELIVERABLE" pill hides in that compressed
state but the orange left rail remains.

## 8. User / Manager mode + per-step content overrides

A header pill toggles **User** (read-only, default) vs **Manager** (inline editing).

- State in `localStorage` key **`avss-mode`** (`'user'` | `'manager'`).
- Edits in `localStorage` key **`avss-step-overrides`**: `{ [stepId]: { actionItem?,
  summary?, details?, notes? } }`. Only changed fields are stored; the renderer merges
  the override over the base step via `effectiveStep(step)`.
- Editable sections in the detail panel: **action item, summary, details, notes**
  (title/owner/num are not editable). Each gets an "Edit" affordance in Manager mode;
  Save writes the override + re-renders that section in place; Cancel reverts.
  Details/notes editors support add/remove rows.
- All user-editable text is HTML-escaped on render via `escHtml()` (XSS-safe).

**The persistence layer is intentionally isolated** to `getOverrides()` /
`saveOverride()` (and `getMode()` / `applyMode()`). When migrating into the Instrata
project tools app, replace the bodies of these functions with backend calls and gate
Manager mode behind the app's real role check — the render layer needs no other changes.

## 10. Local preview & verification

`.claude/launch.json` defines a `process-doc` server (`npx http-server -p 8765`).
After a build, verify via the Preview MCP at
`http://localhost:8765/Process%20Doc.html`. The JS lives in two inline `<script>`
tags; a syntax error there is silent (no console error) but stops init — symptom is the
landing/flow view never renders and `document.body.dataset.mode` is empty. To find such
errors, eval `new Function(scriptText)()` against the 2nd script tag's text. The
Preview screenshot tool has been flaky here; functional checks via `preview_eval`
(navigate by hash, inspect DOM, click toggles) are the reliable verification path.

## 11. Migration target & known quirks

**Destination:** this becomes a feature inside the **Instrata project tools app**.
Keep edit/persistence logic swappable (§8). Pre-sales branch flows, post-sales, and
the detail panel already share one rendering pipeline.

**Known quirks (not bugs — flagged for when real content gets authored):**
- Design-Build Phase 3 has both `M3.1 Functional Sketch` (milestone) and
  `D2 Functional Sketch` (deliverable) — same title, faithful to the source mermaid.
  Rename one when authoring content if it's confusing.
- All `videoUrl` are `''`; the video card is a placeholder UI element only.
- Home-page Pre-Sales card copy still reads generically; fine, but may want a tweak
  ("5 branches") before going live.
- Pre-sales `'TBD'` placeholders are intentional — the team fills them via Manager mode.
